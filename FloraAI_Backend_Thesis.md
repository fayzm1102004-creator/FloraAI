FloraAI: Backend System Architecture & Implementation Thesis
Comprehensive technical documentation covering the system analysis, database design, API routing, security, performance, and testing strategies for the FloraAI backend ecosystem.

Chapter 1: Backend System Analysis & Architecture
1.1 Introduction to the Backend Ecosystem
The FloraAI backend serves as the computational brain and centralized data repository for the broader FloraAI mobile ecosystem. Built upon the robust foundation of C# and the cross-platform capabilities of the ASP.NET Core (.NET 8) framework, the backend is engineered to handle complex diagnostic orchestrations, secure data persistence, and high-latency integrations with artificial intelligence models.
Unlike traditional monolithic applications, the FloraAI backend is uniquely positioned as a "Hybrid AI Orchestrator." It must seamlessly bridge the gap between lightweight, on-device Edge computing (the Flutter client's MobileNetV2 model) and computationally intensive Cloud intelligence (Google's Gemini 2.5 Flash API). This duality necessitates a backend architecture that is inherently resilient, highly scalable, and strictly modular.
1.2 System Requirements
To ensure the architectural integrity and operational success of the backend, a rigorous requirements engineering phase was conducted. The requirements are bifurcated into Functional and Non-Functional specifications.
1.2.1 Functional Requirements
Functional requirements define the explicit behaviors and operational capabilities the backend must possess to satisfy the business logic of the FloraAI application.
1. Identity and Access Management: The system must securely register, authenticate, and authorize users utilizing JSON Web Tokens (JWT), supporting a seamless Refresh Token rotation workflow to prevent arbitrary session termination.
2. Diagnostic Orchestration: The backend must expose an endpoint capable of receiving localized plant disease classifications, subsequently querying the Gemini AI LLM to generate narrative, disease-specific treatment and care protocols.
3. Personalized Plant Libraries: The system must allow users to securely create, read, update, and manage a digital library of their physical plants, maintaining a chronological history of diagnostic scans for each plant.
4. Offline-First Synchronization: The backend must be capable of processing bulk, distributed data payloads generated by the mobile client during periods of network unavailability, executing conflict resolution upon network restoration.
5. Knowledge Base Caching: The system must autonomously capture and persist the outputs generated by the Gemini AI into a centralized ConditionsDictionary, serving as a global knowledge base for future identical queries.
1.2.2 Non-Functional Requirements (Scalability, Security, Latency)
Non-functional requirements dictate the qualitative metrics and architectural constraints that define the system's overall health and user experience.
1. Latency and Performance Optimization: Given the inherent latency of external LLM APIs (averaging 3–5 seconds per request), the backend must implement an In-Memory Caching strategy to reduce response times for previously diagnosed conditions to under 50 milliseconds.
2. System Scalability: The architecture must effortlessly handle concurrent HTTP requests without thread starvation. The utilization of asynchronous programming paradigms (async/await) across all I/O bound operations is mandatory.
3. Data Security and Integrity: Sensitive user data, specifically cryptographic password vectors, must be securely hashed using the BCrypt algorithm. All endpoint access, excluding authentication routines, must be strictly protected via Role-Based Access Control (RBAC).
4. Fault Tolerance and Resilience: The backend must not cascade failures resulting from third-party API outages. The implementation of transient fault handling logic (e.g., Retry and Circuit Breaker patterns via the Polly library) is required for external HTTP communications.
1.3 Architectural Pattern: The N-Tier / Layered Approach
To fulfill the rigorous non-functional requirements and ensure long-term maintainability, the FloraAI backend was architected utilizing the N-Tier (Layered) Architectural Pattern. This design methodology organizes the application into isolated horizontal layers, where each layer possesses a distinct boundary of responsibility and interacts solely with the layer immediately beneath it.
1.3.1 Presentation Layer (Controllers)
The Presentation Layer acts as the singular entry point for all client requests. Implemented via ASP.NET Core Web API Controllers, this layer is deliberately kept "thin." Its strict responsibilities are limited to:
• Intercepting inbound HTTP requests and extracting routing parameters.
• Enforcing endpoint security through [Authorize] attributes.
• Validating the structural integrity of incoming JSON payloads (Data Annotation validations).
• Delegating the execution of business logic to the underlying Services Layer.
• Formatting the ultimate HTTP response and standardizing status codes (e.g., 200 OK, 400 Bad Request).
1.3.2 Business Logic Layer (Services)
The Business Logic Layer represents the computational heart of FloraAI. It encapsulates all domain-specific rules, data transformations, and external API orchestrations.
• Decoupling via Interfaces: Every service (e.g., DiagnosisService, UserService) is abstracted behind a C# Interface. This architectural decision enables Dependency Injection (DI), facilitating isolated Unit Testing by allowing the injection of mock dependencies.
• Orchestration: This layer handles complex workflows, such as the DiagnosisService querying the ConditionService for cached data before deciding whether to invoke the GeminiService via HTTP.
1.3.3 Data Access Layer (Repositories/EF Core)
The Data Access Layer abstracts the complexities of the relational database management system. FloraAI utilizes Entity Framework Core (EF Core) as its Object-Relational Mapper (ORM).
This layer translates the C# domain entities (e.g., User, ScanHistory) into optimized SQL queries. By confining all database interactions to this tier, the system achieves database agnosticism; the underlying SQL Server could theoretically be swapped for PostgreSQL with zero modifications to the Business Logic Layer.
1.4 Justification for Separation of Concerns (SoC)
The paramount academic and practical justification for the N-Tier architecture lies in the principle of Separation of Concerns (SoC).
In a monolithic, unlayered application, business rules, database queries, and HTTP routing are often deeply intertwined. Such tight coupling results in a fragile codebase where a minor database schema modification could inadvertently shatter the API routing logic.
By enforcing SoC, the FloraAI backend achieves several critical software engineering objectives:
1. Testability: Because the Business Logic Layer is entirely devoid of HTTP context and direct database connections, it can be comprehensively validated using high-speed, isolated Unit Tests.
2. Maintainability: Developers can refactor, optimize, or entirely rewrite the Data Access Layer (e.g., writing raw SQL for a complex query) without altering a single line of code in the Business Logic Layer.
3. Team Velocity: Frontend developers can rely on stable, contract-based API endpoints (Presentation Layer) while backend engineers concurrently iterate on the internal AI orchestration algorithms (Business Logic Layer).

Chapter 3: API Design and Endpoints Documentation
3.1 RESTful API Principles in FloraAI
The FloraAI backend was architected strictly adhering to Representational State Transfer (REST) principles. This ensures a stateless, client-server communication paradigm that is both highly scalable and easily consumable by the Flutter mobile application.
Key architectural decisions regarding the API design include:
• Statelessness: Every HTTP request from the mobile client contains all necessary context (e.g., JWT in the Authorization header), eliminating the need for server-side session management.
• Resource-Based Routing: Endpoints are structured around core domain entities (e.g., /api/userplants, /api/diagnosis), utilizing standard HTTP verbs (GET, POST, PUT, DELETE) to denote the intended operational semantics.
• Standardized Responses: All list-based endpoints enforce a generic PagedResponse<T> wrapper to handle pagination, ensuring payload consistency and optimizing bandwidth over mobile networks.
The following sections provide comprehensive technical documentation for the core API endpoints that drive the FloraAI ecosystem.

Chapter 4: Security, Performance & Implementation Details
4.1 Authentication Workflow (JSON Web Tokens)
Security in the FloraAI backend is managed through a stateless authentication architecture utilizing JSON Web Tokens (JWT). This approach eliminates the necessity for server-side session storage, allowing the API to scale horizontally without encountering session consistency bottlenecks.
4.1.1 Token Generation and Payload Claims
Upon successful cryptographic validation of a user's credentials (hiding behind the BCrypt hashing algorithm), the TokenService generates a cryptographic Access Token signed with the HMAC-SHA256 algorithm. The token payload (Claims) embeds critical non-sensitive metadata, establishing the user's identity and permissions for subsequent requests.
C#
// Excerpt from TokenService.cs demonstrating Claim generation
var claims = new List<Claim>
{
    new Claim(ClaimTypes.NameIdentifier, user.Id.ToString()),
    new Claim(ClaimTypes.Email, user.Email),
    new Claim(ClaimTypes.Role, user.Role.ToString())
};

var key = new SymmetricSecurityKey(Encoding.UTF8.GetBytes(_config["Jwt:Key"]!));
var creds = new SigningCredentials(key, SecurityAlgorithms.HmacSha256);
The inclusion of the Role claim enables the application of strictly enforced Role-Based Access Control (RBAC) across administrative endpoints via the [Authorize(Roles = "Admin")] attribute.
4.1.2 Refresh Token Rotation and Blacklisting Mechanisms
Access Tokens are inherently short-lived (e.g., 15 minutes) to minimize the attack window in the event of token theft. To ensure a seamless user experience, a long-lived cryptographically secure Refresh Token is generated and persisted in the database.
When an Access Token expires, the mobile client submits the expired token alongside the valid Refresh Token. The system validates the authenticity of both tokens, invalidates the old Refresh Token, and issues a fresh pair (Refresh Token Rotation).
Furthermore, upon explicit user logout, the system enforces a Token Blacklisting Mechanism via the TokenBlacklistService. The unique identifier (JTI) of the active Access Token is extracted and stored in a highly available Redis cache until its absolute expiration time, effectively revoking access immediately without requiring database I/O.
4.2 Performance Optimization Strategy
Given the computational overhead associated with AI-driven processing and the strict latency requirements of mobile UX, aggressive performance optimization strategies were implemented across the data access and service tiers.
4.2.1 In-Memory and Distributed Caching
The most significant latency bottleneck in the FloraAI architecture involves external HTTP calls to the Gemini LLM. To mitigate this, a sophisticated caching strategy was employed via the ConditionService.
When a diagnostic request is received, the service first queries the local ConditionsDictionary (acting as a persistent cache). For even faster retrieval, frequently accessed statistical data on the Admin dashboard utilizes Redis Distributed Caching.
C#
// Excerpt demonstrating Cache Interception Logic
public async Task<ConditionsDictionary> GetOrFetchConditionAsync(string plantType, string conditionName)
{
    // 1. Intercept: Check persistent cache (Database)
    var cached = await _dbContext.ConditionsDictionary
        .FirstOrDefaultAsync(c => c.PlantType == plantType && c.ConditionName == conditionName);

    if (cached != null) return cached;

    // 2. Cache Miss: Invoke expensive LLM call
    var treatmentText = await _geminiService.GenerateArabicTreatmentTextAsync(plantType, conditionName);

    // 3. Persist and return
    var newCondition = new ConditionsDictionary { ... };
    _dbContext.ConditionsDictionary.Add(newCondition);
    await _dbContext.SaveChangesAsync();
    return newCondition;
}
4.2.2 Database Query Optimization
Entity Framework Core interactions were highly optimized to prevent the "N+1 Query Problem." The Include() operator was systematically utilized across repository methods to enforce Eager Loading for related entities (e.g., retrieving a UserPlant alongside its ScanHistories in a single SQL roundtrip). Additionally, database queries yielding Read-Only data enforce .AsNoTracking() to bypass the EF Core Change Tracker, significantly reducing memory allocation.
4.3 Artificial Intelligence Integration (Gemini API)
The FloraAI backend integrates with Google's Gemini 2.5 Flash API to dynamically generate narrative, contextually aware horticultural advice.
4.3.1 Prompt Engineering and Persona Definition
The system does not merely forward user input to the LLM. Instead, it utilizes an advanced Prompt Engineering architecture that defines a specific AI persona ("Dr. Flora"). The prompt strictly enforces the structural output, commanding the model to bypass standard Markdown formatting and return a rigidly structured JSON object.
This strict separation ensures that the Flutter application receives predictable schema elements (partitioning CareAdvice into 5 distinct fields: Watering, Light, Fertilizing, Soil, Humidity), allowing for granular UI rendering without the risk of parsing malformed text blocks.
4.3.2 Scientific Recommendation Neutrality
A critical design requirement for the FloraAI diagnosis engine is the enforcement of brand-neutrality in medical recommendations. The system is strictly programmed to avoid suggesting specific commercial brand names for pesticides or fertilizers. Instead, the AI provides the "Active Ingredient" (المادة الفعالة) required for treatment.
This approach serves three primary purposes:
1. Universal Applicability: Users in different geographical regions can find the necessary chemical treatment regardless of local brand availability.
2. Professional Accuracy: It aligns with professional botanical and pharmacological standards.
3. User Education: It empowers users to understand the chemical basis of plant care, encouraging more informed decision-making at local agricultural suppliers.
Each treatment recommendation includes a specific instruction in Arabic, guiding the user to inquire about the identified active ingredient at their local horticultural provider.
4.3.2 Resilience and Fault Tolerance (Polly Policies)
Interfacing with third-party APIs inherently introduces the risk of network instability and Rate Limiting (HTTP 429). To guarantee backend stability, the HttpClient associated with the GeminiService was fortified using the Polly resilience library.
• Retry Policy: In the event of transient network failures (HTTP 503 or timeouts), the system is configured to automatically execute an exponential backoff retry mechanism (e.g., retrying up to 3 times, waiting 2, 4, and 8 seconds).
• Fallback Policy: If the LLM integration completely fails, the architecture implements a graceful degradation strategy. The system intercepts the failure and returns a hardcoded, universally applicable set of generic plant care instructions, ensuring the mobile client always receives actionable data rather than an unhandled application exception.

Chapter 6: Testing and Quality Assurance
6.1 Testing Strategy
The testing strategy for the FloraAI backend system was formulated to rigorously validate three primary objectives: Reliability, ensuring consistent operational behavior under varied conditions; Scalability, guaranteeing the system can handle concurrent user requests efficiently; and Accuracy, verifying that the integrations with the Gemini AI model yield correct, contextually appropriate horticultural advice.
To achieve this, the testing methodology adhered to the Testing Pyramid approach. The foundation consists of a vast array of high-speed Unit Tests targeting isolated business logic. The middle tier comprises Integration Tests evaluating the interaction between components (such as the API, Entity Framework Core, and external APIs). The apex of the pyramid consists of end-to-end (E2E) and Functional API Tests, executing full system workflows to emulate actual client-server interactions.
6.2 Unit Testing (Business Logic)
Unit testing forms the bedrock of the FloraAI backend quality assurance process. The tests were implemented using xUnit as the primary testing framework within the .NET ecosystem. To ensure true isolation of the business logic, the Moq library was utilized to construct mock objects for dependencies, such as database contexts and HTTP clients.
Core services, notably the DiagnosisService and ConditionService (the equivalent of PlantManager logic), were rigorously tested to ensure that caching logic, AI fallback mechanisms, and diagnostic formatting operated flawlessly without requiring an active database or network connection.

6.3 Integration Testing (Component Interaction)
Integration testing was conducted to validate the seamless communication between distinct architectural layers and external dependencies.

Rather than mocking the HTTP client, these tests validated the actual network handshakes, assessing the system's ability to negotiate payload transmission, handle API rate limits, and properly enforce the JSON response structure dictated by the prompt engineering constraints.
6.4 Performance & Stress Testing
Performance testing focused on system behavior under load, evaluating concurrent request handling and computational latency.
Given the integration of a Large Language Model (LLM), latency is a primary concern. Stress tests simulated concurrent diagnostic requests from multiple mobile clients. The findings demonstrated that while direct requests to the Gemini API incurred an average latency of 3.5 to 5 seconds, the strategic implementation of In-Memory and Distributed Caching (Redis) drastically altered the performance profile. For cached diagnostic queries, the response time was reduced to under 50 milliseconds. This architectural decision not only bypassed the external API latency but also mitigated third-party operational costs, proving highly effective in handling concurrent traffic spikes.
